# Домашнее задание к занятию «SQL. Часть 2» - Плотников Вячеслав

### Задание 1

**Активный master и пассивный slave:** все изменения и записи идут на главный сервер (master), а резервный (slave) просто копирует эти данные и ждет. Главный плюс — надежность. Если мастер упадет, пассивный сервер можно быстро поднять вместо него. Плюс на этот резервный сервер можно скинуть резервное копирование или тяжелые проверки, чтобы они не мешали основному сайту или приложению. Минус в том, что сама по себе такая пассивная реплика никак не ускоряет чтение данных для пользователей, а при аварии нужно вручную или автоматически переключать систему (failover).

**Master и несколько slave-серверов:** здесь запись тоже идет на один мастер, но читать данные можно сразу с нескольких slave-серверов. Это отлично помогает, когда в приложении намного больше запросов на чтение, чем на запись (что бывает в большинстве проектов). Мы просто распределяем этот поток по репликам и разгружаем главный сервер. Кроме того, если одна реплика сломается, трафик пойдет на остальные. Единственный важный нюанс — задержка репликации: иногда данные на слейве появляются с небольшой задержкой, поэтому сразу после записи критичные вещи лучше читать с мастера.

### Задание 2

## Принципы

**Горизонтальный шардинг:** делим одну большую таблицу на части и раскидываем строки по разным базам в зависимости от ключа (например, пользователей раскидываем по диапазонам user_id, а магазины — по регионам). Структура таблиц везде одинаковая, а приложение само понимает, в какую базу стучаться.

**Вертикальный шардинг:** разделяем таблицы по разным базам в зависимости от того, за что они отвечают. Например, пользователи живут в одной базе, книги в другой, магазины в третьей. Это удобно, чтобы нагрузка не перемешивалась.

## План размещения

Возьмем для примера таблицы:

- users (пользователи);
- books (книги);
- stores (магазины).

Сначала разнесем их по смыслу (вертикальный шардинг): данные пользователей отправляем в UsersDB, каталог книг — в CatalogDB, а магазины — в StoresDB.
Затем внутри этих баз сделаем горизонтальное деление (если данных станет слишком много): пользователей разобьем по диапазонам user_id, а магазины — по регионам (region_id). Каталог книг пока можно оставить на одном сервере, а если вырастет — тоже поделить по ID. Связывать таблицы между собой напрямую через внешние ключи между разными серверами не стоит: лучше передавать ID, а нужные данные забирать через запросы приложения.

```text
								 Приложение
										|
					  Маршрутизатор / каталог шардов
						/             |              \
		 UsersDB (вертикаль)  CatalogDB       StoresDB (вертикаль)
			 по user_id          каталог книг     по region_id
			 /       \                |             /       \
	  U-shard-1  U-shard-2      C-shard-1    S-shard-1  S-shard-2
		 master     master         master        master     master
			 |          |              |             |          |
		 replica    replica         replica       replica    replica
```

## Режимы серверов и обработка запросов

- На каждом шарде крутится один активный master — он принимает все новые записи и изменения.
- У каждого мастера есть одна или несколько реплик (slave). Они работают в режиме чтения и подстраховывают основной сервер на случай сбоя.
- Так как репликация идет с небольшой задержкой, все самые свежие и важные данные запрашиваются с мастера, а обычное чтение можно раскидывать на реплики.
- Специальный роутер в приложении смотрит на ключи (например, user_id или регион) и отправляет запрос на нужный шард.
- Если проект небольшой, на старте можно обойтись одной базой на каждую категорию, а шардирование подключать уже по мере роста нагрузок.
